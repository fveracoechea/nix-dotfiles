# Split nixpkgs Channels by Layer

This flake pulls from two nixpkgs channels. The **Release Channel** (the current release branch) builds the System layer on both hosts: kernel, services, display manager, and the compositor. The **Latest Channel** (`nixpkgs`, `nixpkgs-unstable`) builds the Home layer: apps, CLI, and tooling. Before this, one `nixos-unstable` input fed everything, so a `nix flake update` to get a newer coding agent also moved the kernel and forced a Hyprland source build.

The layer decides the channel, except where the layer is not the real concern. Two cases exist today, and both take the channel of what they belong to rather than the channel of where they sit:

- **Version-coupled to the other side.** The Hyprland satellites (`quickshell`, `hyprpaper`, `hyprshot`, `hyprpicker`, `hyprcursor`, `hypridle`, `hyprlock`) live in the Home layer but track the compositor's IPC and protocol versions, so they come from the Release Channel. Without this they are the most likely breakage in the whole arrangement.
- **In a layer for packaging reasons.** Spotify sits in the darwin System layer only because nix-darwin links `Spotify.app` from `environment.systemPackages` into `/Applications/Nix Apps` for Spotlight and Launchpad. It is an app, so it takes the Latest Channel, and `spicetify-cli` comes from the same channel because spicetify patches the Spotify build it wraps. On `nixos-desktop` spicetify already runs in the Home layer, so no override is needed there.

## Consequences

- `nixpkgs.pkgs` receives an already-built instance, and NixOS asserts that `nixpkgs.config` is empty in that case. So `allowUnfree` and `permittedInsecurePackages` live in `nixpkgsConfig` in `flake.nix`, shared by both instances, and hosts can no longer declare them.
- Home Manager runs on the Latest Channel through a plain `_module.args.pkgs` definition, which replaces the `mkDefault` that `useGlobalPkgs = true` supplies. Both module trees still evaluate Home Manager with the Release Channel's `lib`, so `home.enableNixpkgsReleaseCheck` is off on both hosts. Home Manager and `pkgs` do agree; only `lib` differs, and it supplies pure helpers. A Home Manager release that needs a newer `lib` function would break evaluation with a clear error.
- The Release Channel has one branch per platform: `nixos-YY.MM` for Linux and `nixpkgs-YY.MM-darwin` for macOS, held in two inputs. `stableSourceFor` picks by system, so call sites stay one line. nix-darwin asserts that its own branch corresponds to the Nixpkgs branch it evaluates against, so `nix-darwin` is pinned to `nix-darwin-YY.MM` and follows the darwin release branch. Bumping the release means moving all three refs together.
- The Latest Channel tracks `nixpkgs-unstable`, not `nixos-unstable`. `nixos-unstable` is gated on the NixOS VM integration tests as well as the nixpkgs jobset, so it trails by hours to a couple of days. That gating bought something when this input built the NixOS system; now the System layer comes from the Release Channel and this input builds only Home layers, which those tests do not cover. It is also the branch nix-darwin and standalone Home Manager recommend. `nixos-unstable-small` is fresher still but runs a reduced test set and builds fewer packages, so cache coverage is thinner.
- `inputs.musnix` follows `nixpkgs-stable` and `inputs.nix-darwin` follows `nixpkgs-stable-darwin`. Every other input keeps following `nixpkgs`. There is no `hyprland` flake input: the compositor is a system package like any other and comes from the Release Channel, so it is always a `cache.nixos.org` hit rather than a source build against an overridden nixpkgs. The cost is that its version is the release's. 26.05 holds 0.55.4, the last version that reads `hyprland.conf`; 0.56 dropped hyprlang for `hyprland.lua`. The config must be ported to lua before the release moves to 26.11, and `wayland.windowManager.hyprland.configType` is set explicitly so the two can never drift apart.
- Spotify on macOS is fetched from a `web.archive.org` snapshot on both channels, because Spotify's own CDN serves only the current release. Wayback rate-limits with HTTP 429, so a Spotify version not already in the store can fail to fetch for a while. That is upstream packaging, not a consequence of this split, but it is the first thing to check when a darwin build fails on `SpotifyARM64.dmg`.
- Custom Packages choose their channel per entry in `packages/default.nix`, so consumers keep reading `dotfilesPkgs.<name>` and no call site knows which channel it got.
